# 已确认需求结论

本文件把飞书《待确认需求》的 18 项结论及后续已确认变更转成可执行的产品边界。原始 18 项快照见 `product/data/decision-baseline.csv`。

| 编号 | 当前结论 | 对产品范围的影响 |
|---|---|---|
| REQ-001 | 定量指标的评价等级由完成值和计算规则产生，只读 | V3 必须补齐 PC、移动端、导入和服务端的一致口径；任何人工选择定量等级的页面都不生效 |
| REQ-002 | 系统初评分/初评等级与人工调整结果并存 | 保存系统事实、调整后等级、调整人、调整时间；调整不能反写指标评价和系统得分 |
| REQ-003 | 组织信息完全来自组织人事模块 | 绩效不维护组织单位；V1 的“单位”明确为计量单位（%、元、次、分等），旧原型的组织单位示例无效 |
| REQ-004 | 不增加手动补充活动的额外治理需求 | 保留现有异常补充入口和自动/手动来源；本期不新增补充原因、审批链或第二套复杂防重规则，仍执行通用创建校验和审计 |
| REQ-005 | 自动创建失败由系统补偿，不提示业务用户 | 服务端必须幂等重试并留内部故障记录；补偿成功不产生用户消息，持续失败进入运维处置，不开放人工补偿页面 |
| REQ-006 | 关系模式变化通过方案版本隔离 | 已创建活动保持原版本规则；新活动使用新版本。禁止更新方案时回写进行中活动 |
| REQ-007 | 活动详情支持完整字段、自选字段后导出 | 覆盖人员、目标、考核、审定、面谈、确认和最终结果；导出仍受数据权限和字段权限约束 |
| REQ-008 | 原型不要求穷举完整人员样本 | 需求和测试必须覆盖状态组合；不以原型样本数量作为验收标准 |
| REQ-009 | 工作台信息架构以当前 V2 原型为页面参考 | 只纳入功能清单未标记“不需要”的入口；原型中的 AI 助手、旧进度和异常入口不因此进入 Scope |
| REQ-010 | 输出正式报表需求和指标字典 | 当前只交付目标报表、绩效结果报表和绩效分布报表；进度报表和分析报表已被功能清单排除 |
| REQ-011 | 列全所有消息通知模板 | 产品定义事件、接收人、变量、去重和跳转目标；实现采用固定模板还是配置化由研发设计决定 |
| REQ-012 | 补齐 HRBP 数据录入边界 | V3/V4 必须提供角色×活动状态×人员范围×数据类型×可写字段矩阵 |
| REQ-013 | 保留人员、目标、考核、审定、面谈五类导入 | 每类导入都必须说明适用状态、当前节点影响、流程去向、冲突处理、部分成功和审计 |
| REQ-014 | 暂不提供申诉处理台账和处理结果留痕 | 保留员工申诉提交产生的原始事实和 HRBP 授权查看；不提供线上受理、进度、结论或处理记录。若要完全取消申诉，必须同步将 PF-259～PF-265 改为“不需要”，当前清单没有这样标记 |
| REQ-015 | 移动端覆盖工作台和表单处理/审批 | 移动端不承载基础配置、方案、活动管理、批量导入导出和报表管理 |
| REQ-016 | 报表先自选字段再导出 | 可选字段不得突破当前用户的数据范围和敏感字段权限；不提供“一键导出全部隐藏字段” |
| REQ-017 | 输出 V5 正式 PRD | 本地与飞书均需形成可直接交付研发和测试的 V5 文档 |
| REQ-018 | V6 暂不输出 | AI 表单、监控、分析和移动端能力不进入当前 Scope，不从原型占位自动转成需求 |
| REQ-019 | 逐级审定不使用循环节点或循环取处理人 | 汇报线和组织层级模式均在流程模型中固定枚举 8 个逐级审定节点；每个节点分别配置对应层级处理人，空处理人自动跳过并审计，不再使用停止人员或停止组织动态结束 |
| REQ-020 | 同一活动只有一个全局业务环节，个人只允许处于该环节内的不同流程节点 | 环节开启/结束按全部适用参与人批量执行；个人按照考核组绑定流程流转，不得把个人流程节点展示成多个业务环节并行 |
| REQ-021 | 首个环节未结束前允许补加参与人，首个环节结束后禁止补加 | 首环节未开始或进行中可补加；暂停、截止已过或结束处理中禁止；补加人从首节点开始并继承原截止时间，首环节结束后只能新建关联补充活动 |
| REQ-022 | 环节自动/强制结束对未完成人员直接给配置等级并跳过后续 | 撤销其当前待办，个人考核旅程进入强制结束终态；不得伪造表单、审批、认可或申诉记录，已完成当前环节人员继续后续环节 |
| REQ-023 | 当前人员状态变化只处理离职，不支持调岗和组织变化专项逻辑 | 离职进入异常并允许管理员终止未完成个人流程；调岗/组织变化不触发自动移除、重分组、换当前处理人或参与人调整 |
| REQ-024 | 考核组条件按原型补充到 V3.1 | 支持部门、岗位、职级、区域、人员类型、人员状态、指定人员、排除人员，并明确跨维度、优先级和唯一匹配规则 |
| REQ-025 | 目标导入暂存区允许删除单条目标，正式提交时统一校验 | 删除时不立即阻止；提交时按员工校验必填、唯一键和权重 100%，失败员工不提交，其他员工可成功 |
| REQ-026 | 结果认可与申诉均为不可逆终态 | HRBP 对申诉只读，无审批、驳回、修改或结果登记；系统强制结束不得伪装成员工认可 |
| REQ-027 | 强制分布区分个人提交和考核组审定完成 | “不超过”在个人提交时校验，“不低于”在组完成时校验；未产生有效等级人员只进分母，组内仍有处理中人员时禁止完成 |
| REQ-028 | 自动创建主活动名称按“年份+周期名称+方案名称”生成，不可人工改 | 年份取具体绩效周期年份且只出现一次；周期名称用月度/Q1/H1/年度等业务名；不添加多余分隔符。手动补充活动仍允许人工填写名称 |
| REQ-029 | 活动列表行操作只保留查看、删除 | 暂停/恢复/正常结束/提前终止等生命周期动作保留在活动详情；删除仅未进入执行且无正式业务记录时可执行，其他状态可展示禁用删除并提示 |
| REQ-030 | 参与人列表展示目标审批状态 | 枚举仅限未开始、制定中、已生效；不适用目标制定的人员显示“—”；制定中含填写中、待审批、驳回后重填 |
| REQ-031 | 允许在当前全局业务环节内为未开始员工手动开启个人流程 | 不允许给单个人开启另一个业务环节；单人开启须原子创建个人流程、首节点待办并触发任务到达通知，重复点击幂等拒绝 |
| REQ-032 | 当前活动不支持人工修改员工考核关系 | 去掉活动详情与批量中的“修改考核关系”；保留查看考核关系、方案锁定/动态配置，以及流程转交/调整当前待办处理人 |
| REQ-033 | 目标/考核/审定导入仅处理对应环节个人流程未开始的被考核人 | 成功后形成活动级导入结果并标记“已通过导入完成”，后续开启不再启动个人流程、不发待办；已有流程/待办/在线正式提交的员工导入失败；允许部分成功与导入更新追溯 |
| REQ-034 | 批量或单人开启时同步创建并发出首节点待办 | 状态校验、个人流程创建、首节点待办属于同一业务操作；页面不提供单独“发送待办”；待办创建失败则该员工不得进入已开始；消息渠道失败不回滚业务流程但须记通知失败 |
| REQ-035 | 业务导入均为活动级导入 | 活动由页面上下文确定，模板不要求用户填写活动编码/名称或模板编号/名称；工号匹配被考核人；目标更新以工号+目标名称匹配，无法唯一匹配则该行失败 |
| REQ-036 | 统一使用“操作日志”名称与字段模板 | 列表可精简列，详情展示完整字段；覆盖自动创建命名、删除、单人开启、批量开启、导入完成跳过、导入更新等动作 |

## 冲突处理结果

- 旧项目说明把绩效面谈列在结果确认之后；当前 V2 功能清单分组、已确认方案 PRD、方案原型和 Spec 一致采用“目标→面谈→考核→审定→确认”，本基线以该顺序为准；月度不启用面谈。
- 旧 Spec 中“绩效组织单位”统一改为“计量单位”；组织、部门、岗位、职级和汇报关系都属于外部组织人事模块。
- 原型中的“手动补充活动”不是主路径，但仍是当前异常补充入口；REQ-004 只否决新增治理层，不删除入口。
- 原型中的“申诉 3 个工作日处理”等承诺无效；当前只提交申诉、通知 HRBP 并提供只读查看，不形成待处理审批，也不在线处理。
- 原型中所有 AI 助手区域均属于 V6 占位，当前版本不验收。
- 线上目标、结果、分布报表目前存在空白渲染错误，V5 PRD 必须靠指标字典和验收标准完整定义，不能依赖该页面自行说明。
- 旧文档中的“循环逐级取人”“到停止人员结束”“到停止组织结束”均失效；以 REQ-019 和 `BR-039` 的固定 8 节点口径为准。
- 旧活动原型中“个人处于多个业务环节”的表达失效；活动只有一个全局业务环节，个人差异只发生在该环节内的流程节点。旧“禁止给单个人开启”已由 REQ-031 修正为：禁止给单个人开启另一个业务环节，允许在当前全局业务环节内为尚未开始且符合条件的员工手动启动个人流程。
- 原型中的“不确认驳回”“超时自动确认”不是合法结果确认状态；分别使用“已申诉”和“系统强制结束”。
- 调岗和组织变化相关操作日志、自动换人和自动移除示例不进入当前版本；当前人员状态异常只支持离职。
- 活动内“修改考核关系”入口与日志示例失效；以 REQ-032 为准，当前版本不支持人工修改员工考核关系。
