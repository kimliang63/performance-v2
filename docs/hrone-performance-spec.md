# 01 Project

## 01.1 项目目标

HRONE 绩效模块必须支持企业从绩效规则配置、绩效方案设计、考核活动执行到绩效结果沉淀的完整业务闭环。

系统必须满足：

- COE 统一维护绩效规则与绩效方案。
- SSC 基于方案发起并管理具体考核活动。
- 员工、管理者和 HRBP 按角色完成目标、面谈、考核、审定、部门考核数据录入、确认与申诉。
- 同一方案允许在多个同类型绩效周期复用。
- 活动必须固化方案版本、方案配置、基础规则内容与具体周期；活动创建后的配置变化只影响新活动。
- 已正式提交的业务结果必须保留提交时实际使用的规则内容，禁止因基础规则后续变化自动重算。
- 正向、驳回、暂停、终止、超时与申诉场景必须形成明确业务结果。
- 原型、业务规则、验收标准和版本 Scope 必须可统一引用。

## 01.2 系统边界

### 01.2.1 绩效模块负责

- 绩效周期与绩效规则管理。
- 绩效方案、考核组和考核环节设计。
- 考核活动创建、参与人确定、环节管理和过程监控。
- 目标制定、绩效面谈、绩效考核、结果审定、结果确认与申诉。
- 员工与管理者绩效工作台。
- 目标、绩效结果和绩效分布报表。
- 绩效业务触发的通知内容、接收对象和触发条件。
- 绩效业务数据的有效性、历史追溯和结果锁定规则。

### 01.2.2 依赖外部平台能力

| 外部能力 | 绩效模块的依赖 | 边界引用 |
|---|---|---|
| 组织中心 | 员工、部门、岗位、职级、汇报关系、双线关系和 HRBP 归属 | `EXT-ORG` |
| 权限中心 | 菜单、操作和数据范围授权 | `EXT-PERM` |
| 流程引擎 | 流程模型、节点流转、待办、转交、驳回和自动节点 | `EXT-FLOW` |
| 公式编辑器 | 计算表达式配置、校验和执行 | `EXT-FORMULA` |
| 消息中心 | 飞书等渠道的消息投递、失败重试和送达记录 | `EXT-MESSAGE` |
| 文件能力 | 业务附件、导入文件和导出文件的存取 | `EXT-FILE` |

### 01.2.3 边界原则

- 绩效模块必须定义业务触发条件和业务结果。
- 外部平台必须负责其通用能力。
- 绩效模块禁止重新建设流程设计器、组织中心、权限中心、消息中心和公式编辑器。
- 外部平台能力不足时，必须记录为依赖缺口，不得在 Spec 中假设已经支持。

## 01.3 设计原则

### P-001 Prototype Reference

高保真原型只负责页面职责、页面关系和交互体验参考。原型不是业务 Scope 或规则来源；与功能清单、已确认决策或 Spec 冲突时必须登记差异并以业务基线为准。Spec 禁止重复定义页面布局、组件样式和视觉细节。

### P-002 Business Rule First

所有业务行为必须由业务对象、生命周期、业务规则、权限规则或数据约束定义。页面不得形成独立业务口径。

### P-003 Configuration to Execution

绩效业务必须遵循“基础规则 → 绩效方案 → 考核活动 → 业务环节 → 绩效结果”的分层关系。

### P-004 Immutable Activity Snapshot

活动创建时必须固化方案版本、方案结构、实际使用的基础规则内容与具体周期。方案或基础配置后续变化禁止影响既有活动；新活动使用变更后的新版本或新配置。已正式提交结果还必须保留本次实际使用的快照内容以供追溯。

### P-005 Single Rule Source

状态只在 State Machine 定义；权限只在 Permission Rule 定义；业务约束只在 Business Rule 或 Data Constraint 定义；页面只引用 Prototype。

### P-006 Explicit Decision

未确认业务不得由 AI Agent 或研发人员补全。冲突、歧义和缺失必须进入 `02.5 Requirement Discovery`。

### P-007 Version by Delta

版本 Scope 只记录新增、变更、删除和未纳入项，禁止复制完整系统定义。

### P-008 Automation First

绩效活动的主业务路径必须由方案配置自动创建活动、确定考核关系并推动环节流转。手动补充和人工干预只用于异常补漏，仍须使用已启用方案、相同创建校验和操作审计，不得形成绕开方案规则的第二套主流程。

### P-009 Role-oriented Delivery

每个版本 PRD 必须面向前端、后端和测试三类研发团队角色组织内容。三个角色视图必须引用同一组 Spec 规则和原型，不得分别定义业务口径。

## 01.4 Non Goal

本 Spec 不负责：

- 定义前端、后端、接口、数据库、微服务或部署方案。
- 描述页面布局、样式、字体、间距、动画和控件实现。
- 重新定义流程引擎、组织中心、权限中心、消息中心和公式编辑器。
- 规划流程引擎平台自身的功能与版本。
- 在 V6 Scope 确认前定义 AI 功能。
- 把历史 PRD、Mock 数据或原型占位内容自动视为当前业务规则。

## 01.5 Spec Update Rule

出现以下任一已确认变化时，必须更新本 Spec：

- 项目目标、系统边界或角色职责变化。
- 业务对象、对象关系、生命周期、状态或终态变化。
- 业务规则、权限规则、数据约束或公共交互规则变化。
- 外部通用能力的使用条件、依赖边界或禁止事项变化。
- 原型中的页面职责、业务动作、业务跳转或业务结果变化。
- 新增正常、异常、边界或权限场景，需要形成验收标准。
- 版本 Scope 新增、删除或改变业务能力。
- 评审发现冲突并形成最终业务结论。

以下变化禁止直接更新业务规则正文：

- 仅页面布局、样式、文案排版或控件视觉变化，只更新原型。
- API、数据库、前后端、部署或技术架构变化，只更新工程设计文档。
- 当前评审进度、负责人、计划时间、缺陷状态或开发状态，只更新项目状态记录。
- 尚未形成结论的讨论、建议和会议意见，只进入 Requirement Discovery 或评审记录。
- 为符合既有 Spec 而进行的原型修复，不产生新的业务规则。

更新时必须修改规则的唯一来源，并同步检查受影响的 Capability、Prototype Reference、Acceptance 和 Version Delta；禁止在版本 PRD 或会议记录中复制形成第二套规则。

# 02 Business Knowledge

## 02.1 Domain Model

### 02.1.1 配置对象

| 业务对象 | 定义 | 主要关系 |
|---|---|---|
| 绩效周期 | 一段可被活动选择的考核时间范围 | 被考核活动引用；引用约束见 `DC-001` |
| 计量单位 | 指标、衡量标准和完成值使用的业务计量单位，例如%、元、次、分 | 由绩效基础配置维护；组织信息依赖 `EXT-ORG` |
| 等级规则 | 绩效等级、顺序、名称、区间和展示语义的集合 | 被方案和强制分布规则引用 |
| 计算规则 | 定量指标完成值转换为计算结果，并可继续转换为评价等级的业务规则 | 依赖 `EXT-FORMULA` |
| 衡量标准 | 指标目标值、挑战值、保底值或等级标准 | 被指标引用 |
| 指标 | 目标或考核中使用的评价对象 | 引用衡量标准和计算规则 |
| 评价规则 | 指标评价等级与业务分值的映射 | 被考核组和考核环节引用 |
| 强制分布规则 | 各绩效等级的人数或比例约束 | 必须绑定等级规则 |

### 02.1.2 方案对象

| 业务对象 | 定义 | 主要关系 |
|---|---|---|
| 绩效方案 | 可跨多个同类型周期复用的考核业务模板 | 引用周期类型、等级规则、考核组和环节配置 |
| 考核组 | 方案内按人员规则划分的考核范围 | 引用组织信息、评价规则和环节规则 |
| 环节配置 | 方案中某个业务环节的启用、流程和规则集合 | 受 `BR-001` 环节顺序约束 |
| 活动管理员预设 | 方案预设的活动管理责任人 | 创建活动时带入，活动允许按规则确定最终管理员 |

### 02.1.3 执行对象

| 业务对象 | 定义 | 主要关系 |
|---|---|---|
| 考核活动 | 某方案版本在某个具体绩效周期中的执行实例 | 持有方案与基础规则快照、周期快照和创建来源 |
| 活动参与人 | 进入活动的被考核员工 | 归属一个考核组并产生环节进度 |
| 业务环节实例 | 某活动当前统一执行的业务环节状态 | 同一活动同一时刻最多一个进行中业务环节，遵循 `SM-003` |
| 个人流程实例 | 某参与人在当前业务环节中按考核组绑定流程执行的实例 | 同一业务环节内个人可处于不同流程节点 |
| 待办 | 需要特定处理人完成的业务任务 | 依赖 `EXT-FLOW` |
| 异常事项 | 活动、人员或环节中需要关注的异常 | 可触发提醒或管理动作 |

### 02.1.4 业务记录对象

| 业务对象 | 定义 | 主要关系 |
|---|---|---|
| 目标记录 | 员工在目标制定环节提交的目标内容 | 有效性见 `DC-004` |
| 考核记录 | 员工或考核人在绩效考核环节提交的评价内容 | 计算规则见 `BR-020`～`BR-028` |
| 面谈记录 | 员工提交并由上级确认的绩效面谈内容 | 有效性见 `DC-004` |
| 审定记录 | 各级审定人提交的绩效等级调整结果 | 受强制分布约束 |
| 结果确认记录 | 员工对最终绩效结果的认可或申诉状态 | 每人每活动唯一，见 `DC-005` |
| 申诉记录 | 员工对绩效结果提出异议的业务记录 | 处理规则见 `BR-040`～`BR-044` |
| 最终绩效结果 | 活动中对员工形成的最终绩效等级与相关结果 | 确认完成后锁定 |
| 操作记录 | 对关键业务动作的追溯记录；业务统一名称“操作日志” | 记录要求见 `DC-008`、`BR-077` |

### 02.1.5 核心关系

```text
基础规则
  └─被绩效方案引用
      ├─包含考核组
      └─包含启用的业务环节
          └─实例化为考核活动
              ├─绑定具体绩效周期
              ├─包含活动参与人
              ├─产生全局业务环节实例
              ├─为适用参与人产生个人流程实例
              ├─产生待办与业务记录
              └─形成最终绩效结果
```

## 02.2 Lifecycle / State Machine

状态名称、允许动作和终态只在本节定义。其他章节必须引用 State Machine 编号。

### SM-001 绩效方案

| 当前状态 | 允许变化 | 业务约束 |
|---|---|---|
| 草稿 | 启用、删除 | 启用前必须满足方案完整性规则 |
| 已启用 | 停用 | 允许被新活动选择 |
| 已停用 | 重新启用 | 禁止被新活动选择；不影响已有活动 |

### SM-002 考核活动

| 当前状态 | 允许变化 | 业务约束 |
|---|---|---|
| 未进入执行 | 进入执行、删除 | 允许调整未锁定的活动信息 |
| 执行中 | 暂停、正常结束、提前终止 | 允许管理环节和参与人 |
| 已暂停 | 恢复执行、提前终止 | 暂停期间禁止继续推进业务环节 |
| 已正常结束 | 无 | 终态 |
| 已提前终止 | 无 | 终态 |

### SM-003 全局业务环节实例

| 当前状态 | 允许变化 | 业务约束 |
|---|---|---|
| 未开始 | 开启中、已跳过、已终止 | 必须满足环节开启条件 |
| 开启中 | 处理中、未开始 | 为全部适用参与人批量创建个人流程；失败时保持未开始并补偿 |
| 处理中 | 结束中、已暂停、已终止 | 由个人流程终态和方案结束策略共同决定 |
| 结束中 | 已完成、处理中 | 正常结束或强制结束的个人处理全部成功后才能完成 |
| 已暂停 | 处理中、已终止 | 恢复后继续原业务环节和个人节点 |
| 已完成 | 无 | 终态 |
| 已跳过 | 无 | 终态，结果处理按对应业务规则执行 |
| 已终止 | 无 | 终态 |

### SM-003A 个人流程实例

| 当前状态 | 允许变化 | 业务约束 |
|---|---|---|
| 未创建 | 处理中、已通过导入完成 | 全局环节批量开启，或当前全局环节内单人开启时创建；目标/考核/审定导入成功可直接进入已通过导入完成 |
| 处理中 | 已完成、已暂停、已终止、强制结束 | 个人可处于该业务环节内不同流程节点；进入处理中时必须同时成功创建首节点待办 |
| 已通过导入完成 | 无（本环节） | 本环节不再启动个人流程或待办；按导入结果作为本环节完成结果；个人流程启动前允许按导入规则更新 |
| 已暂停 | 处理中、已终止、强制结束 | 恢复后继续原节点 |
| 已完成 | 无 | 当前业务环节正常完成，可进入下一全局业务环节 |
| 已终止 | 无 | 合法终止，不再产生新的个人业务记录 |
| 强制结束 | 无 | 使用方案配置等级形成系统结果并跳过全部后续业务环节 |

### SM-003B 目标审批状态（参与人展示）

| 状态 | 含义 |
|---|---|
| 未开始 | 该员工没有目标导入结果，且目标流程尚未启动 |
| 制定中 | 目标流程已启动但尚未全部审批生效；填写中、待审批、驳回后重填均归入制定中 |
| 已生效 | 目标已完成审批，或通过目标导入规则直接形成有效目标 |
| — | 不适用目标制定环节的人员；禁止伪造状态 |

### SM-004 目标制定

```text
员工提交 → 间接/双线上级审批 → 直接/直线上级审批 → 目标生效
```

- 间接/双线上级驳回：退回员工。
- 直接/直线上级驳回：退回员工。
- 员工重提后必须重新经过完整审批链。
- 空审批人必须由流程引擎按 `EXT-FLOW` 自动跳过。

### SM-005 绩效面谈

```text
员工提交面谈记录 → 直接/直线上级确认 → 面谈完成
```

- 上级驳回：退回员工。
- 员工重提后必须重新经过上级确认。

### SM-006 绩效考核

```text
员工自评 → 间接/双线上级评分 → 直接/直线上级评分 → 考核完成
```

- 间接/双线上级或直接/直线上级驳回：退回员工自评。
- 驳回后，本轮基于旧完成值形成的有效评分全部失效。
- 员工重提后必须重新经过完整评分链。

### SM-007 结果审定

```text
直接/直线上级审定 → 间接/双线上级审定 → 固定枚举逐级审定节点（1～8）→ 条件性 HRBP 审批 → 审定完成
```

- 逐级审定必须使用流程模型中预置的 8 个固定节点；各节点分别配置对应层级处理人，禁止运行时循环生成节点或循环取处理人。
- 固定节点处理人为空时必须自动跳过并记录原因；8 个节点全部处理或跳过后进入 HRBP 条件分支。
- HRBP 审批只在方案定义的目标等级条件满足时触发；当前规则为 A 级。
- 间接/双线上级、逐级上级或 HRBP 驳回：退回直接/直线上级重新审定。
- 驳回后，旧审定结果不得继续计入当前强制分布。

### SM-008 结果确认与申诉

| 当前状态 | 员工动作 | 目标状态 | 后续业务结果 |
|---|---|---|---|
| 待确认 | 认可结果 | 已认可 | 结果确认流程结束 |
| 待确认 | 提交申诉 | 已申诉 | 通知 HRBP 后自动结束结果确认流程 |
| 已认可 | 无 | — | 终态 |
| 已申诉 | 无 | — | 终态；申诉在线下处理 |

- 结果确认禁止驳回。
- HRBP 通知节点禁止形成待处理审批动作。
- 申诉禁止自动修改或解锁最终绩效结果。

## 02.3 Business Glossary

| 术语 | 统一定义 |
|---|---|
| COE | 绩效规则和绩效方案的业务管理角色 |
| SSC | 负责在授权范围内发起并管理考核活动的共享服务角色 |
| HRBP | 负责授权部门考核数据录入、条件性审定审批和申诉查看的角色 |
| 被考核人 | 参与考核活动并形成绩效结果的员工 |
| 直接/直线上级 | 员工的直接汇报上级 |
| 间接上级 | 直接上级的直接上级 |
| 双线上级 | 由组织资料独立维护的另一条汇报关系上级 |
| 逐级上级 | 由固定枚举的逐级审定节点分别解析出的对应层级审定人；当前预留 8 个节点，不使用循环取人 |
| 周期类型 | 月度、季度、半年度、年度或自定义等方案分类，不是具体绩效周期 |

# 04 Constraint

## 04.1 Business Rule

### 环节与方案

| 规则编号 | 规范性规则 |
|---|---|
| BR-001 | 所有启用环节必须遵循“目标制定→绩效面谈→绩效考核→结果审定→结果确认”的相对顺序。 |
| BR-002 | 月度考核禁止启用绩效面谈。月度启用目标、考核、审定和确认时，顺序必须为目标→考核→审定→确认。 |
| BR-003 | 绩效方案必须绑定周期类型，禁止绑定具体绩效周期。具体周期必须由考核活动选择。 |
| BR-004 | 已停用方案禁止发起新活动；已存在活动必须继续使用活动快照。 |
| BR-005 | 方案启用前必须具备完整基本信息、至少一个考核组、至少一个启用环节及所有必需引用规则。 |
| BR-006 | 活动参与人必须且只能归属一个最终生效考核组。考核组匹配冲突必须按方案配置优先级处理；相同优先级仍冲突、零匹配或条件无法解析时不得静默选组。 |
| BR-007 | 已启用自动创建的方案必须按照方案配置，在绩效周期开始前或开始后指定天数自动创建对应周期的考核活动。自动创建必须是活动创建的主业务路径。自动创建主活动名称必须按 `BR-070` 生成。 |
| BR-008 | 考核关系配置为“锁定”时，必须在创建活动时确定并固化参与人及其考核关系，后续组织关系变化不得自动替换该活动中的考核关系。 |
| BR-009 | 考核关系配置为“动态”时，必须在流程节点到达处理人时，按照方案规则和当时有效的组织关系解析实际处理人；此前尚未到达的节点禁止预先锁定处理人。 |
| BR-016 | 绩效基础配置中的单位只表示指标和完成值的计量单位；组织、部门、岗位、职级、汇报关系和 HRBP 归属必须来自组织人事模块，绩效禁止复制维护组织主数据。 |
| BR-017 | 自动创建活动必须按“方案版本+具体周期”幂等；失败由系统自动补偿，补偿结果不向普通业务用户发送提示，持续失败进入内部故障处置。 |
| BR-018 | 手动补充活动只用于异常补漏，仍须选择已启用方案版本并执行与自动创建相同的配置、权限、周期、人员和重复校验；本期不增加补充原因或额外审批链。 |
| BR-019 | 活动暂停必须挂起全部未终态环节和在途待办并阻止新正式提交；恢复必须从原节点继续；提前终止必须撤销全部在途待办并拒绝迟到提交。 |
| BR-061 | 同一活动同一时刻最多一个业务环节处于开启中、处理中、结束中或已暂停；业务环节必须对全部适用非终态参与人批量开启或结束。个人差异只允许存在于该业务环节内的流程节点。禁止给单个人开启另一个业务环节；允许在当前全局业务环节已开启/处理中时，为尚未开始且符合条件的单个员工手动启动该环节个人流程。 |
| BR-062 | 活动参与人只允许在首个业务环节未开始或处理中时补加；首环节已完成、已终止或进入结束中后禁止补加。活动或首环节暂停、原截止时间已过、或自动结束任务已开始时同样禁止补加。 |
| BR-063 | 补加参与人必须立即完成权限、重复、唯一考核组和关系校验，并从首个业务环节的首节点创建个人流程；任一步失败必须整体回滚。补加人继承原首环节截止时间，并立即进入参与人数、进度、强制分布分母和通知范围。 |
| BR-064 | 首环节结束后发现漏人时，只能创建与主活动关联的补充活动。补充活动使用同一方案版本和周期，从首环节开始，人员不得与主活动或其他未终态补充活动重叠；报表汇总主活动和补充活动，主活动结束不等待补充活动。 |
| BR-065 | 方案配置的自动/强制结束触发后，对当前环节未完成的个人流程撤销待办、标记强制结束、跳过该参与人的全部后续业务环节，并以方案配置等级形成系统来源最终结果；禁止伪造表单提交、审批、认可或申诉。已完成当前环节人员继续后续环节。 |
| BR-066 | 当前人员状态变化专项处置只支持离职。离职员工不得从既有活动中自动删除；系统形成离职异常，管理员可终止其未完成个人流程并留痕。 |
| BR-067 | 调岗和组织变化当前不触发自动移除、考核组重匹配、当前处理人替换或参与人调整。动态关系仍只按 `BR-009` 在未来节点到达时解析。 |
| BR-068 | 考核组人员条件支持部门、岗位、职级、区域、人员类型、人员状态、指定人员和排除人员；同维度多值为“或”，跨维度为“且”，排除人员优先于指定人员和条件命中。 |

| BR-014 | 目标总权重必须等于 100%。 |
| BR-015 | 目标审批必须针对整份目标记录，禁止单独审批某条目标或指标。 |

### 绩效计算

| 规则编号 | 规范性规则 |
|---|---|
| BR-020 | 定量指标必须由用户填写完成值，并使用指标引用的计算规则产生计算结果；计算结果可按配置转换为评价等级。定量指标的评价等级必须由系统生成并只读展示，禁止用户自行选择或修改。 |
| BR-021 | 每个指标评价等级必须取所引用评价规则中该等级对应的业务分值。定量指标使用系统转换出的评价等级，定性指标使用有权限的当前处理人选择的评价等级。 |
| BR-022 | 单节点初评分必须等于各指标评价等级对应分值按指标权重汇总后的结果，并计入方案允许的加分与减分；系统必须由该初评分映射出初评等级。有权限的当前处理人允许调整初评等级，但调整不得修改指标评价等级、等级对应分值或系统初评分。 |
| BR-023 | 最终考核得分必须等于各有效考核节点初评分按方案节点权重汇总后的结果。 |
| BR-024 | 考核等级必须由最终考核得分映射至方案引用的等级规则；等级禁止参与前述得分计算。 |
| BR-025 | 完成值允许的数值类型与精度必须由指标或衡量标准定义。 |
| BR-026 | 指标得分、权重汇总和节点汇总过程中禁止额外取整；最终考核得分必须四舍五入保留两位小数。 |
| BR-027 | 考核等级必须使用保留两位小数后的最终考核得分进行等级区间映射。 |
| BR-028 | 系统禁止设置统一的默认最高分或最低分；需要限制得分范围时，必须由计算规则明确表达。 |

### 强制分布与审定

| 规则编号 | 规范性规则 |
|---|---|
| BR-030 | 强制分布分母必须为考核组内参与考核的总人数，包含跳过审定人员和未完成审定人员。 |
| BR-031 | 某等级分子必须为该等级当前有效人数；同一员工在同一考核组内禁止重复计数。 |
| BR-032 | 跳过审定人员必须使用方案配置的固定等级，并计入对应等级分子。 |
| BR-033 | 未产生有效等级的人员只计入分母，不计入任何等级分子。 |
| BR-034 | 强控模式下，“不超过”约束必须在个人审定提交时阻断超限提交；“不低于”约束必须在考核组完成审定时阻断完成。弱控模式下必须提示偏差并允许提交或完成。 |
| BR-035 | 审定驳回或重提后，旧等级必须立即退出当前有效分布统计。 |
| BR-036 | 强制分布规则允许以人数或比例表达，并允许配置“不超过”或“不低于”约束；考核组人数达到配置的生效人数后方可应用，未达到时禁止执行分布控制。 |
| BR-037 | 人数规则必须直接使用配置人数；比例“不超过”的人数上限必须按“考核组人数×配置比例”向下取整；比例“不低于”的人数下限必须按该结果向上取整。 |
| BR-038 | “不超过”约束必须在每次个人审定提交时实时校验；“不低于”约束必须在考核组完成审定时校验。审定完成后，强制分布规则变化禁止重新校验或改变历史结果。 |
| BR-039 | 汇报线和组织层级逐级审定都必须在流程模型中固定枚举 8 个逐级审定节点，每个节点分别配置对应层级处理人；禁止运行时循环生成节点或循环取人，也不得依赖“停止人员”或“停止组织”动态结束。固定节点处理人为空时必须自动跳过并记录原因，禁止产生无人处理待办。 |

|---|---|

### 批量处理

| 规则编号 | 规范性规则 |
|---|---|
| BR-050 | 批量导入范围包括活动参与人、目标、考核、审定和面谈；必须按单条业务记录分别校验和处理。目标、考核、审定、面谈等业务导入必须从具体活动上下文发起。 |
| BR-051 | 部分记录失败时，成功记录必须保留，失败记录必须返回明确失败原因（含员工标识）。 |
| BR-052 | 批量导入的正式业务结果必须遵循对应参与人、目标、考核、审定或面谈 State Machine。 |
| BR-053 | 批量导入和导出必须记录操作人、业务范围、时间和结果，并写入操作日志。 |
| BR-054 | 目标、考核、审定导入每条记录必须校验：人员属于当前活动与操作者授权范围；活动未暂停/终止/结束；导入类型与对应业务环节一致；该员工对应环节个人流程未开始。已创建个人流程、已发出待办或已产生在线正式提交的员工必须导入失败。人员导入与面谈导入仍按现行允许范围执行。活动暂停或终态时禁止形成新正式结果。 |
| BR-055 | 导入不得与在线流程结果并行有效。个人流程启动前，已导入数据允许按导入规则更新并保留操作追溯，禁止静默制造重复有效记录。导入与在线提交并发时只允许一个业务版本成功。 |
| BR-056 | 目标、考核、审定导入成功后，该员工形成对应类型的活动级导入结果，并在对应环节标记“已通过导入完成”；后续批量开启或单人开启不得再为其启动个人流程，不得创建待办或发送任务到达通知。开启日志必须记录因导入结果跳过。面谈导入成功后仍按约定进入后续确认节点。 |
| BR-057 | 考核导入只接受完成值和允许人工填写的定性评价；定量评价等级必须由活动快照中的计算规则重新生成，禁止从文件覆盖系统评价等级。 |
| BR-058 | 目标导入解析后的暂存区允许删除单条目标；删除本身不阻止后续操作。正式提交时必须按员工重新校验必填、唯一键、至少一条有效目标和权重合计 100%；失败员工不形成记录，其他合法员工可继续成功。目标导入完成后目标审批状态为“已生效”。 |
| BR-060 | 绩效通知必须定义业务事件、接收人、发送时点、内容变量、去重键和业务跳转；消息投递失败不得回滚已完成业务事务，但必须记录通知失败结果供重试和审计。 |
| BR-069 | 已认可和已申诉均为不可逆结果确认终态。系统按 `BR-065` 强制结束时只能记录“系统强制结束”，不得写成员工认可、员工申诉或 HRBP 处理。 |
| BR-070 | 系统自动创建的主活动名称必须自动生成为“年份+周期名称+方案名称”：年份取具体绩效周期年份且最终名称中只出现一次；周期名称使用月度、Q1、Q2、H1、年度等业务名称；不添加多余分隔符；不允许人工输入或修改。示例：`2026年Q2标准季度考核方案`。手动补充活动仍允许人工填写活动名称。 |
| BR-071 | 活动列表每行业务操作仅允许“查看”和“删除”。删除仅当活动未进入执行且不存在正式业务记录时可执行；其他状态可展示禁用删除并提示原因，删除前必须二次确认。暂停、恢复、正常结束、提前终止等生命周期能力保留在活动详情，不得出现在列表行操作。活动名称链接进入详情不构成第三种业务操作。 |
| BR-072 | 当活动当前全局业务环节已开启/处理中，且某员工在该环节个人流程仍为未开始时，活动管理员可手动开启该员工个人流程。成功时必须在同一业务操作内：创建个人流程、创建首个有效待办、触发任务到达通知、更新员工状态/当前处理人/更新时间并写操作日志。活动暂停、终态、环节结束中/已结束，或员工已开始/已完成/已终止/已通过导入完成时禁止开启。重复开启必须幂等拒绝，不得产生重复流程或待办。页面成功反馈必须明确“个人流程已开启，待办已发送”。 |
| BR-073 | 当前活动不支持人工修改员工考核关系。禁止提供修改考核关系的独立操作或批量操作。允许查看考核关系；方案层锁定/动态考核关系配置继续有效；流程转交或调整当前待办处理人不视为修改考核关系。 |
| BR-074 | 批量开启全局环节时，对已标记“已通过导入完成”的适用人员必须跳过个人流程与待办创建，并在操作日志中说明跳过原因；其余适用人员按 `BR-075` 处理。 |
| BR-075 | 批量开启全局环节与手动开启单个员工时，状态校验、个人流程创建、首节点待办创建必须属于同一业务操作；成功后立即触发任务到达通知。页面禁止提供单独“发送待办”动作。待办创建失败时该员工不得进入已开始状态。批量开启仍须保持一致性：失败不得形成半开环节。 |
| BR-076 | 导入模板由活动页面上下文确定活动；用户不填写活动编码、活动名称、模板编号或模板名称。模板版本如需校验，只能作为文件元数据。工号匹配当前活动被考核人；目标更新以“工号+目标名称”匹配，同一员工目标名称在当前活动内必须可唯一匹配，否则该行失败。 |
| BR-077 | 关键业务动作必须写入操作日志，字段至少覆盖 `product/templates/operation-log-template.md` 定义；业务统一名称为“操作日志”。 |

## 04.2 Permission Rule

| 权限编号 | 规范性规则 |
|---|---|
| PR-001 | 员工只能查看和处理自己的目标、考核、面谈、确认、申诉和绩效结果。 |
| PR-002 | 管理者只能查看和处理其组织关系或流程任务授权范围内的员工数据。 |
| PR-003 | COE 负责绩效基础规则和绩效方案维护。 |
| PR-004 | SSC 负责在授权范围内发起并管理考核活动、参与人、环节和异常事项。 |
| PR-005 | HRBP 只能查看其授权范围内员工提交的原始申诉事实；禁止对申诉执行受理、同意、不同意、驳回、修改、进度登记或结果登记。 |
| PR-006 | 所有页面和业务动作必须同时满足功能权限与数据范围权限。 |
| PR-007 | HRBP 只允许在授权部门、当前活动状态和当前业务节点范围内导入人员、目标、考核、审定和面谈允许字段，并按流程执行条件性审定审批；除该授权数据录入外，HRBP 默认禁止发起或管理考核活动。 |
| PR-008 | SSC 允许在其活动和数据授权范围内导入人员、目标、考核、审定和面谈；导入不能扩大其活动权限，也不能绕过当前人员节点。 |

## 04.3 Data Constraint

| 约束编号 | 规范性约束 |
|---|---|
| DC-001 | 被考核活动引用的绩效周期禁止修改起止时间或删除。 |
| DC-002 | 一个绩效方案允许被多个同周期类型的考核活动复用。 |
| DC-003 | 活动创建时必须固化方案版本、方案结构、当时有效的基础规则内容及具体周期。方案或基础规则后续变化禁止改变既有活动；新活动使用变更后的配置。 |
| DC-004 | 目标、考核、面谈和审定每次正式提交必须形成新的业务记录；被驳回或被替代记录必须保留并标记为作废。 |
| DC-005 | 每名员工在一个考核活动中只能有一条结果确认记录；已认可和已申诉均为终态。 |
| DC-006 | 方案或基础规则变更只影响变更后创建的活动。既有活动中尚未开始和正在进行的动作都必须使用活动快照，禁止读取新配置改变当前活动口径。 |
| DC-007 | 强制分布统计必须以每名员工唯一的当前有效审定等级为准。 |
| DC-008 | 正式提交、审批、驳回、申诉、暂停、恢复、转交、终止、导入、导出、单人开启和个人流程跳过必须可追溯，并符合操作日志模板。 |
| DC-009 | 报表必须使用当前授权范围内的正式业务记录；作废记录禁止计入当前统计结果。 |
| DC-010 | 每次正式提交必须保留本次计算、评价或审定实际使用的规则内容或等价可追溯版本。基础规则后续修改禁止触发已提交记录自动重算。 |
| DC-011 | 指标或衡量标准被引用形成正式目标后，目标中的指标名称、目标值、挑战值、保底值、权重及其他承诺内容必须固化；基础配置后续变化只影响使用新活动快照的新目标。 |
| DC-012 | 报表等级分布的分母必须与强制分布一致，使用考核组参与考核总人数；未出结果人员保留在分母并单独展示。 |
| DC-013 | 强制结束结果必须保存方案版本、业务环节、触发规则、配置等级、原个人节点、撤销待办结果和发生时间；同一参与人只能有一个当前有效最终结果。 |
| DC-014 | 活动参与人清单在首个业务环节完成后冻结；主活动与补充活动的人员集合不得重叠。 |

| EXT-FORMULA | 计算表达式定义、校验和执行必须引用公式编辑器 | 禁止在页面中形成独立计算口径 |
| EXT-MESSAGE | 飞书等渠道的投递、重试和送达记录必须引用消息中心 | 禁止把消息投递成功等同于业务审批通过 |
| EXT-FILE | 附件、导入和导出文件必须引用统一文件能力 | 禁止为单一页面建设独立文件存储规则 |

`EXT-*` 仅为 Spec 文档引用锚点，不是数据库标识、接口字段、平台业务编码或外部能力真实 ID。

## 04.5 Global Interaction Rule

| 规则编号 | 规范性规则 |
|---|---|
| GIR-001 | 页面职责、页面关系和视觉交互可以引用当前 V2 高保真原型；原型中的 Mock 数据、占位功能和错误业务文案不得扩展 Scope 或覆盖 Spec。 |

- 新业务事实必须更新对应唯一章节。
- 版本 PRD、研发设计和测试设计必须引用本 Spec 编号。
- 版本文档禁止重新定义已有 State Machine、Business Rule、Permission Rule 或 Data Constraint。
- 规则变化必须记录影响的 Capability、Prototype Reference、Acceptance 和 Version Delta。
- 被替代内容必须标记为废弃并移入历史归档，禁止与当前规则并列生效。

## 07.5 版本 PRD 交付结构

版本 PRD 是本 Spec 在具体版本中的角色化交付视图，不是新的业务事实来源。每个版本 PRD 必须先定义版本 Scope Delta，并对 Scope 内每个功能提供以下内容：

### 公共功能信息

- 功能名称、职责、版本变化类型和不在本版本范围内的内容。
- 对应 Capability、业务对象、Prototype、State Machine、Business Rule、Permission Rule、Data Constraint 和 Acceptance 编号。
- 涉及角色、前置条件、触发条件、输入、输出及业务结果。

### 前端阅读视图

- 页面职责、用户流程、页面间业务跳转和可执行业务动作。
- 字段名称、业务含义、类型、必填性、可编辑性、默认值、可选值、显示条件和业务校验。
- 不同角色、权限、状态下的展示与操作差异。
- 正常、空数据、校验失败、无权限、流程异常和终态的页面反馈要求。
- 页面布局、组件样式和交互表现必须引用 Prototype，禁止在 PRD 中复制 UI 设计。

### 后端阅读视图

- 业务数据来源、数据责任方、引用的业务对象及外部能力。
- 业务触发时点、原始输入、处理顺序、计算逻辑、校验逻辑、状态变化和业务输出。
- 正向、驳回、撤回、重提、跳过、终止、重复提交、并发和异常场景的业务结果。
- 历史追溯、有效记录、作废记录、快照和版本隔离要求。
- 禁止在版本 PRD 中定义 API、数据库表、接口字段或技术实现方案。

### 测试阅读视图

- 按正常、异常、边界、权限和逆向场景引用或补充 Acceptance。
- 明确场景前置业务状态、业务输入、允许动作、预期状态变化和预期业务结果。
- 覆盖角色越权、数据越权、重复操作、空数据、规则边界、流程驳回、配置变化及外部能力异常。
- 只定义验收口径，不编写具体测试执行步骤。

每个功能必须覆盖三个角色视图。某个角色在该功能中没有变化时，必须明确标记“本版本无角色影响”，禁止直接省略。三个视图重复出现的业务规则必须统一引用 Spec 编号，不得复制规则正文。
